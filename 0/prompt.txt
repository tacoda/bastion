  - Other functions: `router::provider::register`, `router::provider::list` (reports `credential_source` as config/env/secret/none, plus `credential_ref` and `credential_error`, never the value), `router::provider::update_credential` (OAuth write-back), `router::on_secret_changed`, and `router::on_config_changed`.
  - The router binds `secrets::changed`, so a rotated key takes effect without a restart.
  - It registers its entry through `configuration::register` with the text "Provider credentials, routing heuristics, and stream budgets for llm-router." Inferred: the entry id is `llm-router`.
  
  **secrets 0.1.6:**
  - Functions: `secrets::set` (store `vault`, which is encrypted and referenced as `secret://NAME`, or store `env`, which writes to `.env`), `get`, `list`, `delete`, `access`, `resolve`, `compare-and-set`, `detect`, `import`, `status`, plus the `secrets::changed` event.
  - Only allowlisted **consumers** (worker names) can resolve a secret. A caller that isn't on the list gets `SECRET_FORBIDDEN`. Grant access with `secrets::access`.
  - The vault master key comes from `III_SECRETS_KEY` or a key file.
  
  ## OpenAI-compatible hosts (Together, Fireworks, Qwen, Kimi, OpenRouter)
  
  - provider-openai is described as "OpenAI Responses provider worker with Chat Completions compatibility". Its strings include Chat Completions fields such as `max_completion_tokens` and `stream_options`. The router passes it `api_url`.
  - **Inferred, not confirmed:** setting `providers.openai.api_url` probably sends requests to any compatible host. I couldn't find how the worker chooses between the Responses and Chat Completions endpoints. Test this before relying on it.
  - **Running several instances looks unsupported.** The provider id `openai` is hardcoded next to `OPENAI_API_KEY`, and the providers map is keyed by that id. A second compose entry such as `provider-openai#together` would register as `openai` again and collide ("latest-wins"). I didn't find an option to rename the provider id. Inferred, so test it if it matters.
  - So today Bastion gets **one** OpenAI-compatible endpoint, through `providers.openai.api_url`, plus the dedicated deepseek, xai, and zai packages.
  
  ## Recommendation
  
  1. For each provider, call `secrets::set {name: "ANTHROPIC_API_KEY", value, store: "vault", consumers: ["llm-router"]}`.
  2. Use `configuration::set` on the llm-router entry to set `providers.<id>.api_key = "REDACTED"`, plus `api_url` where it's needed.
  3. Read status back from `router::provider::list`. It reports `credential_source` without ever returning the key.
  4. Add `provider-zai` (GLM) and `provider-deepseek` as compose containers. They need no `config_override`.
  5. For Qwen/DashScope, Kimi/Moonshot, Together, or Fireworks, point the single `openai` slice's `api_url` at one of them for now. Supporting several at once would need a new iii provider package, or a Bastion-written provider worker that implements the same `router::provider::register` and `resolve` protocol.
  
  Two things to check before building on this:
  - **Consumer name:** that `consumers` should be `llm-router` (the router does the resolving, not the provider) is my reading of the strings.
  - **Engine fallback:** a failed lookup still falls back to env vars. To fully remove the env dependency, also drop those vars from the stack's environment.
