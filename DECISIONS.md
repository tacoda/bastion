# Bastion decisions

<!-- voice-register: informational -->

Bastion is an agent control plane. You define workflows and send requests,
and Bastion fulfills each request as a job: agents work through the
workflow's steps, which a person can watch and gate, and the job ends with
its branch ready. Bastion is a server and its clients: `bastion-server` runs
jobs on the iii engine, and clients such as the iced desktop app reach it
over HTTP.

This file holds the goals and the decisions the code cites as
`DECISIONS.md D<n>`. The plans that built Bastion, phase by phase, are in
git history.

## Goals and non-goals

**Goals:**

1. A person sees what every job does and decides what it may do.
2. A change Bastion lands passed the checks the owner asked for, with the
   evidence on the job.
3. A restart, an outage or a lost VM never loses a record or corrupts a job.
4. Any client and any number of servers, through one API.

**Non-goals for now:** a web client, managed hosting, a plugin system for
code-defined guards (rules stay data, per D20 and D26), and a sign-in with a
Claude subscription (D36). Multi-user servers and hosting stay open
questions (below), not non-goals.

## Decisions

Each decision keeps the number the code cites. Numbers not listed were
retired with the old plan.

| # | Decision |
|---|---|
| D1 | Rust for all Bastion code. Another language only where no Rust path exists, named here with its reason: `.pi/extensions/entire/index.ts` is generated by the Entire tool and is not Bastion code. |
| D4 | One dark theme, purple as the main color. Its tokens live in `crates/bastion-desktop/src/theme.rs`. |
| D6 | Every Bastion worker is a Rust binary on `iii-sdk` 0.25.0, started by compose through `scripts.run`. |
| D7 | A stock iii worker comes first. Bastion writes a worker only for what no pinned worker does. |
| D8 | Records live in the `database` worker as typed columns. Each row carries a `rev`, and a stale write is refused. |
| D10 | Updates are pushed, never polled: the server observes the engine, and clients follow the server's events (D29). |
| D13 | The local server starts the stack (`iii compose`) and attaches to one that already runs. The stack goes down when the server stops. A client attaches to the local server or starts it, and quitting a client leaves both running. |
| D14 | Every agent turn runs in an `iii-sandbox` VM on its job's worktree. No credential enters an agent's VM. A shell step that needs one asks for it (D40). |
| D16 | A note on a step goes to the agent word for word as its next brief. A fix loop stops after a set count, or sooner when a refusal repeats word for word. |
| D17 | Every job runs a workflow. A free-form task is the shipped Short workflow, not a second mode. |
| D18 | The rules a job runs by live in `bastion-core`: pure functions from an event and a state to a new state and effects, with no I/O and no `async`. |
| D19 | The seams are Cargo dependencies, and `scripts/check-seams.sh` fails CI when one is crossed. Only the engine adapter imports `iii-sdk`. Clients depend on `bastion-protocol` and the client library only. |
| D20 | Every constraint and capability is enforced in a hook, and its rung is data, so an eval can name what changed. |
| D21 | The audit record is a hash chain with one writer. Each entry carries an HMAC-SHA256 of its fields and the entry before it, keyed with a secret outside the record. |
| D22 | An eval compares two harness configurations on the same requests from the same commit, and reports the difference with the decisions behind it. |
| D23 | The tracker, model providers and notifications are adapters behind seams, chosen in Settings. Pull requests, CI and merges are a workflow's shell steps (D39). |
| D25 | Every rule belongs to one layer: the charter (the repository's own), the harness (an agent's calls), or the factory (the workflow). Under review: the harness's and the factory's rules are moving onto workflows and their steps (see the open questions). |
| D26 | Rules, grants and settings are data in the server's database, versioned, edited on the pages; first-run defaults come from `seed/governance.sql`. |
| D27 | The server is the source of truth and holds all business logic. A client shows state and sends a person's actions, nothing more. |
| D28 | The API is HTTP with JSON, one route per action on one resource, typed in `bastion-protocol`, with a bearer token on every request. |
| D29 | Push is server-sent events on `GET /events`, with ids. A client that reconnects with `Last-Event-ID` gets what it missed, or a `resync`. |
| D30 | A client keeps a list of servers, each a name, a URL and a token in the OS keychain. `local` is the server on this machine. A job runs on one server. |
| D31 | A server has people with roles: an admin manages it, a member submits and acts on their own jobs, a viewer reads. Tokens are issued, shown once and kept as a hash. Every record names its actor. |
| D32 | A server listens on loopback unless it has a TLS certificate and key. |
| D33 | Each step is lights-on or dark. A workflow's level follows from its steps. No step waits on a timer. Every decision is logged, whatever the dial. |
| D34 | Model provider keys live in the stack's vault, read only by `llm-router`, never in the environment and never returned. |
| D35 | A workflow is a graph of steps a person edits on a canvas. Steps pass declared results to the steps linked after them. |
| D36 | Claude takes an API key only. No Claude subscription sign-in. |
| D37 | The desktop client is a native Rust app on `iced`. It holds no job or workflow logic and reaches a server only through the client library. |
| D38 | Every client goes through `crates/bastion-client`: the server list, typed calls, and the event stream. A new interface adds pages, not a second way to talk to a server. |
| D39 | A workflow is a series of steps, and nothing else runs. A step is a prompt, an agent (`.agents/agents`), a skill (`.agents/skills`) or a shell script (D45), each with one text. Bastion's built-in stages are gone. |
| D40 | A shell step runs in the job's VM, with no network unless it asks. A step that asks gets a VM of its own with the network and the vault secrets it names as environment variables. |
| D41 | A job ends with its branch ready. When the last step passes, a workspace set to merge merges the branch into its base on the host; one set to leave keeps the branch. |
| D42 | Governance is per step. A step may change files or only reads, and the gate refuses a write from a step that only reads. Dials, notices, artifacts and evals name steps. |
| D43 | A step may name its own model and budget. The model wins over the job's and the server's. The budget is how often its failure may send work back (two by default) and the most its turns may cost; past the cost, Bastion starts no more turns there by itself, but a person's retry, note or answer still runs. |
| D44 | A step is known as `workflow/step`. A grant may be for one workflow step, and it wins over the grant for its kind; a constraint may apply at some steps only, and with none named it applies at every step. The gate reads the step from the turn. |
| D45 | A step is a prompt, an agent, a skill or a shell script. A repository's command is not a kind of its own: a prompt that reads its file does what it did, and that is what migration 7 makes of each command step. This narrows D39. |
| D46 | A repository's charter is `AGENTS.md` and `.agents/`: `.agents/settings.json` holds its permissions and hooks, and `.agents/agents` and `.agents/skills` hold the agents and skills its steps run. Bastion assumes no one vendor's files. The harness, the rules on an agent's calls, is Bastion's own. |
| D47 | A link may be a failure link: when its step fails, the job goes along it instead of back to the step that writes. A failure link orders nothing, so it may go back to an earlier step; a step reached only by failure links is skipped otherwise. The failing step's revisions bound any loop, and past them a person decides. A step has at most one failure link. |
| D48 | A grant is ask or allowed; a call no grant covers is refused, so there is no denied grant. Demoting a grant from ask removes it. A step's own grants, when it has any, take the place of its kind's, so a step is narrowed by listing what it may call. This replaces D44's "wins over its kind's". |
| D49 | A grant on `sandbox::exec` may name a command, and then it covers only a line that starts with those words and has no shell operators. A turn may call the four sandbox tools and every function its step's grants name, and the gate judges every call a turn makes, whatever the function. |
| D50 | A constraint may be a hook: a command that runs in the job's VM before each matching call at its steps, after the charter's hooks, unless it is only told. Exit 2 refuses the call. An owner's constraint can be removed; a charter's changes in its repository. |
| D51 | A constraint may name a reviewer from `.agents/agents/`. When its step finishes, the reviewer reads the step's change in a turn with no tools, from its file at the job's base, and its fail fails the step as D47 says. A reviewer that can't run leaves the job with a person. |
| D52 | A server's MCP servers reach a turn through `workers/bastion-mcp`, which registers each tool as `mcp::<server>::<tool>`. Only MCP servers over HTTP: a stdio server would run on the host, outside the VM. A server's token stays in the vault, and only the bridge may read it. |
| D53 | A step's rules live with the step, on the Workflows page, in one tab by layer: the charter (read-only, from the repository), the harness (grants, and the rules and hooks on calls), and the factory (review checks and reviewers). With no step picked, the page shows what applies at every step. Each rung is a switch. There is no Constraints or Capabilities page. |
| D54 | A constraint or a grant is one item that three scopes turn on or off: all workflows (`*`), one workflow, and one step, each with `!` for off. The most specific setting wins. A list with no `*` means every step when it turns no step on, and only the steps it names otherwise. A grant is an item for one kind and one function; a step turns items on or off rather than replacing its kind's grants, which replaces D48's "take the place of". A rung belongs to the item, not to a scope. |
| D55 | A constraint is judged by an agent (a told rule, a reviewer) or by code (a word match, a hook, a review check). Promoting a told rule gives it a deterministic form; demoting keeps the form and stops running it. |
| D56 | A constraint or capability is feedforward, which guides the agent before it acts (a rule it is told, a skill, an agent, a note on what it may do), or feedback, which checks what it did (a word match, a hook, a review check, a reviewer); it comes from the workspace's charter or from Bastion. Told, checked and enforced give way: a feedforward rule is said to the agent, a feedback one always blocks, and a grant keeps ask or allowed. Items are on or off at a step or for every step of a workflow; the level for every workflow stays in the data but out of the app for now. |
| D57 | Rules live on three pages, Constraints, Capabilities and Permissions, each with a Global view and a Workflows view that picks the workflows and steps an item applies to. A step lists what applies at it, read-only. The charter shows on a Workspaces page; Bastion still applies it, but it is not edited with Bastion's rules. This replaces D53's "no Constraints or Capabilities page". |

## Open questions

- **Dark to merge.** ghola never lets a factory merge unattended; Bastion's
  dark dial can run to merge. Should merge always need a person, or a machine
  verdict, such as the `verify.yaml` contract?
- **Configuration in git.** ghola keeps configuration in files under review;
  Bastion keeps it in the database with versions (D26). Should rules also be
  importable as files, such as team rule packs shared by servers?
- **Multi-user hosting.** A shared server with people and TLS works today.
  Is hosted Bastion a goal?
- **Unused engine workers.** C4 lists them; some may be the harness's
  dependencies.
- **Harness and factory.** D25's two layers are collapsing onto workflows
  and their steps: a step's grants, constraints, model and budget all live
  on the step. Should the split stay, or should Bastion apply everything
  from the settings of a workflow and its steps?
