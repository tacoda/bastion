The problem

Agents write code fast. Trusting what they wrote is the slow part.

The report isn't the work

An agent can say it finished work that its commits don't hold. The gap shows up in the diff, if anyone reads it.

Rules in a prompt drift

A prompt can say "keep the tests," but nothing measures whether the agent listened. So there's no way to tell if a stricter rule helps or only costs more.

The agent holds your keys

An agent that can push and merge has your credentials in its run. And a run that has seen a credential can't be trusted again.

Sessions don't add up

Five agents in five terminals is five things to watch, and nothing says which one is waiting.

The solution

Treat each request as a job, and keep every decision that matters with you.

One board for every job

Each request becomes a job with its own worktree and sandbox VM. The Jobs page shows them all, with the ones waiting on you first.

You judge artifacts, not claims

Every stage leaves something you can check, such as a plan, a test result, or a diff. A comment on one goes to the agent as its next brief.

Rules you can measure

Every rule is a hook decision with a level: told, checked, or enforced. Run an eval to see what a stricter level does before you commit to it.

Keys stay out of the sandbox

Agents run in sandbox VMs that never see a credential. Pushes and pull requests happen on the host, and a tamper-evident log records every decision.

The oversight dial

Start with the lights on. Dim them one checkpoint at a time.

A new factory stops at every checkpoint and asks you. Each checkpoint has its own dial, so as you verify a stage and trust it more, you turn that one darker and leave the rest alone. ask waits for you, hold waits 30 minutes and then goes on, and auto goes on at once.

Use cases

What you'd hand to Bastion this week.

Issue to pull request

Clear small tickets from your backlog

Start a job from a GitHub issue. Bastion opens the pull request and links it back. If CI fails, Bastion sends the agent one more turn with the failing log. When you approve the merge, the issue closes.

issue #1planbuildPR #2CI fixmerge
Review by diff

Steer the work with line comments

Read the proposed diff and leave a comment on a line. The agent gets it word for word, and the next diff answers it, with no chat window.

calc.py:5 · "raise on zero"-    return a / b+    if b == 0:+        raise ZeroDivisionError("b is zero")+    return a / b
Your rules, enforced

Hold agents to your repository's charter

Bastion reads the rules and hooks your repository already has in .claude/settings.json. So a hook that refuses rm refuses it inside the sandbox too.

refused · rm -f /work/repo/notes.txt
PreToolUse hook · exit 2
Eval before you enforce

Find out what a stricter rule costs

Run the same requests with a rule told and with it enforced, then compare. In one small run of three requests, enforcing a rule cut tool calls from 33 to 17 at the same grade.

told → enforced
calls 33 → 17 · cost $0.0344 → $0.0207 · grade 7 → 7

What it is not

  • Not an editor. The only code you see is the diff a job proposes. "Open in editor" hands the worktree to your own editor.
  • Not an agent chat. You talk to a job through its artifacts and checkpoints.
  • Not Windows. Sandbox VMs need Apple Silicon or Linux with /dev/kvm.

Get started

You need Rust, iii 0.25.0, and a model provider key such as ANTHROPIC_API_KEY. The README lists the rest.

git clone https://github.com/tacoda/bastion
cd bastion
cargo tauri dev

Then go to Engine and press Start. If something is missing, Doctor names it and says how to fix it.

Start one job on a small repository this week, and comment on its plan before you approve it.
