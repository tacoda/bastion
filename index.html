How a job runs

A job is one request against one repository, like a ticket. It gets its own worktree, its own sandbox VM, and one pipeline run. The smallest pipeline has five stages:

plan approve build review land

Agent stages run turns in the sandbox. Person stages, marked ◆, are checkpoints where you decide. Each checkpoint has a dial: ask waits for you, hold waits 30 minutes and then goes on, and auto goes on at once. Merge never goes below hold.

Every stage leaves an artifact you can judge, such as a plan, a test result, or a diff. If you comment on one, the comment goes to the agent word for word as its next brief. So a line comment on calc.py:5 comes back answered in the next diff. These fix loops stop after a set count, or sooner when the same refusal repeats.

The full pipeline adds scope, discovery, acceptance tests that must fail before the change and pass after it, a refactor pass, and a code review turn. That work is phase A8, and it's still in progress.

Governance you can measure

A rule that lives only in a prompt can't be measured. So in Bastion every rule is a hook decision, and its position on a ladder is data. You move a rule one rung at a time, and the audit log records each move.

Constraint: what a turn must or must not do

toldThe rule is in the brief.
checkedA hook records each breach.
enforcedA hook refuses the call.

Capability: what a turn may call

deniedThe gate refuses the call.
askThe call waits for you.
allowedThe call runs.
heldplan turn wants to write notes.mdcapability: ask
Allow onceRefuse

A held call. Allow once runs exactly that call. Refuse sends the refusal back to the agent.

Rules come from three layers. The charter is the repository's own, read from its .claude/settings.json and hooks. Then the harness binds each call in a turn, and the factory binds review, land, pull requests, and merges. You edit the harness and factory rules on their pages while jobs run, and the gate reads them again before each turn.

Evals that show what a change does

An eval runs two harness configurations on the same requests and the same repository snapshot. Then it reports the difference, with the hook decisions behind it. Trial jobs stop at review, so nothing lands.

In one recorded run, three requests each asked for a wc count. Arm A had no-wc told, and arm B had it enforced. All six runs reached review.

An audit record that notices tampering

The audit log is a hash chain with one writer. Each entry carries an HMAC-SHA256 of its fields and of the entry before it. The key lives in the macOS Keychain, not in the database, so whoever can edit the database can't recompute the chain.

audit log · verifyverified · 335 entriesone byte of entry 20 changed · verifyfailed at entry 20

An illustration of two checks from a recorded run. Verify runs on the Audit Log page.

The limits matter too. The chain detects a change, but it can't stop one, and it can't tell when someone cuts entries from the end. A remote append-only copy would close that gap, and that copy doesn't exist yet.

Bastion servers

The factory runs in bastion-server, one Rust binary. The app is a client that shows state and sends your decisions, so jobs keep moving with the window closed. The app starts a server on this machine, called local. You can add other Bastion servers, and each one holds its own repositories, each with its own setup, checks, and tests.

You pick the server when you start a job. The Jobs page lists the jobs of every server, and it says when one can't be reached.

Agent turns run in iii-sandbox VMs, and a credential never enters a VM. That is why pushes and pull requests happen on the host. And the engine listens on loopback only.

What it is not

  • Not an editor. The only code you see is the diff a job proposes. "Open in editor" hands the worktree to your own editor.
  • Not an agent chat. You talk to a job through its artifacts and checkpoints, not a prompt box.
  • Not multi-user. One owner, no sign-in. The actor on each record is your git config user.name.
  • Not hosted. It runs on your machine, or on a box you own.
  • Not Windows. Sandbox VMs need Apple Silicon or Linux with /dev/kvm.

Try it

You need these first:

  • Rust from rust-toolchain.toml (rustup picks it up), and the wasm32-unknown-unknown target.
  • cargo install tauri-cli trunk
  • iii 0.25.0 on your PATH.
  • A model provider key, such as ANTHROPIC_API_KEY or OPENAI_API_KEY, in the environment you start Bastion from.
  • gh, signed in, for pushes and pull requests. Landing locally works without it.
git clone https://github.com/tacoda/bastion
cd bastion
cargo tauri dev

Then go to Engine and press Start. Bastion runs Doctor and brings up the stack. If something is missing, Doctor names it and says how to fix it, and a failed required check stops the start.

Start one job on a small repository this week, and comment on its plan before you approve it. PLAN.md has the phases and says which layer owns what.
